### Task 1 review round 1

The independent review re-ran the evidence (115 and 1353 passes, no lints, byte-identical
fixtures). It reported two findings. Both were verified against the wire captures and fixed
test-first.

1. **Blocker: the 5-minute/1-hour cache split was lost at `message_delta`** (inherited from the
   plan-literal `anthropic_usage()`). The verified wire capture (report 07 section 3.14) has a
   `message_delta` that repeats the cumulative `cache_creation_input_tokens` without a
   `cache_creation` object. The else-branch overwrote the split from `message_start` with "all
   5-minute writes" and set `cache_write_1h = 0`. For example, a 0/7448 split became 7448/0, so
   1-hour writes (BP1/BP2 default, architecture section 6.11) were priced at the 5-minute rate.
   The goldens missed it because `thinking_tools` uses the older `message_delta` shape, with
   output tokens only.
   Fix: new `anthropic_cache_total()`. A bare total updates the split: a split that adds up to
   the total is kept; otherwise the known 1-hour writes are kept and the rest are 5-minute writes
   (or the reverse when only the 5-minute writes are known). Only when no split was ever reported
   is every write a 5-minute write (report 07 section 3.5). A `cache_creation` object counts as a
   split only when it carries one of the two `ephemeral_*` keys. `usage.iterations` is not used,
   because its relation to the top-level totals (for example with compaction) is unverified.
2. **Major: a null in `message_delta` wiped known usage to unknown** (introduced by D-022.1).
   `message_delta` usage is cumulative, and a null in it means "no update" (report 03 section
   2.5.1, lines 363-364; the SDK's MessageDeltaUsage). The adaptation recorded the null as `NA`.
   With a start of 10 input and 300 cache-read tokens, a delta of nulls gave input `NA`, total
   `NA` and cost unknown. A null `cache_creation_input_tokens` also forced `cache_write_1h = 0`,
   and a null `cache_creation` subfield became a known 0 through `%||% 0`.
   Fix: new core helper `adp_usage_set()`. A value replaces the earlier one. A null keeps the
   earlier value and is `NA` only when nothing was recorded before. It applies to the top-level
   fields, the `cache_creation` subfields and `thinking_tokens`. A null bare total leaves both
   split fields untouched. Merge semantics apply to `message_start` as well, which is equivalent
   there because it is the first usage report of a message. `adp_count()` now holds the shared
   nonnegative-count check that `adp_usage()` used inline.

D-022 point 1 now describes the merge rule, and a new point 5 records the cache split.

Two regression tests were added (8 assertions):
- "a bare cache total in message_delta keeps the 5-minute/1-hour split (07 3.14)" covers the
  wire shape through both `push()` and `push_parsed()`, a grown total, and the case with no
  split at all.
- "a null in message_delta keeps the value reported before it (cumulative, IC-74)" covers the
  reviewer's scenario, null split and thinking fields after known values, a null split field
  with no earlier value (now `NA`), and that value then derived from a later bare total.

### Task 2 review round 1

The independent review re-ran the evidence (215 focused and 4224 neighbour passes, the same two

1. **Major: provider headers came from the global record only** (plan-literal
   `adp_provider_headers(model)`). The helper looked the provider up again with
   `provider_get()`, which never sees a session-scoped (rank 0) record. P05's `provider_stream()`
   had already resolved that record and passed it as `opts$provider`, with `opts$session` set.
   Contract 10.1 scopes `model = <spec>` to its session, and 10.2 row 1 gives provider specs
   `headers`, so the finding is real. Such a provider's headers were dropped. When a session
   record shadowed a global one with the same id, the global record's headers were sent with
   the session record's base URL and credential. The plan's Tasks 5, 7 and 9 reuse the helper.
   Fix: `adp_provider_headers(model, opts = NULL)` uses `opts$provider` when the model's provider
   is its id, name or one of its aliases. Otherwise it uses the session's own record

   `provider_get()`. `anthropic_build()` passes `opts`. The argument is optional, so the
   plan-literal calls of Tasks 5, 7 and 9 still run, but those tasks must pass `opts` (D-023).
   Layering is unchanged: `ext-registry.R` is L0 and `provider-registry.R` is in the same area.
2. **Nit: a budget equal to `max_tokens`.** With `max_output <= 1024`, the plan's clamp
   `min(budget, max(1024, max_tokens - 1024))` gave `budget_tokens = max_tokens`. That breaks

   `thinking` and no interleaved-thinking beta, and `max_tokens` returns to the requested value

   reviewer's proposal. The reviewer would drop thinking whenever `max_tokens - 1024 < 1024`,
   that is, for any `max_tokens` up to 2047. That would also drop it for 1025-2047, where
   `budget_tokens = 1024` is valid. Here thinking is dropped only when no valid budget exists
   (`max_tokens <= 1024`). No catalog model is affected.

### Task 2 review round 2

The second independent review re-ran the evidence: `^provider-anthropic$` at 227 passes, the
neighbours at 4236, both with the same two dependency skips, and no lints. It diffed the tree
against the plan: the source is plan-literal apart from the D-023 changes, `skip_without_run_engine()`
and the two round-1 regression tests. It reported one major finding and one nit. Both were
checked against the contract and fixed test-first. D-023 items 3 and 4 record them.

1. **Major: provider headers were appended without deduplication.** The plan's
   `headers = c(headers, adp_provider_headers(model, opts))` repeated a name when the record set
   one the adapter also sets. Contract 10.2 row 1 allows any named list of non-secret strings, and
   `providers.<id>.headers` in settings feed it too. P04's `http_headers()` refuses a spec that
   repeats a name in any case (`gptr_error_invalid_argument`), so the request never left the
   process. With an `anthropic-beta` record header, only requests where gptr adds its own beta
   failed (an OAuth token, budget thinking, inline tool additions), so the failure could appear
   mid-session. The finding is real.
   Fix: the shared helper `adp_merge_headers(base, extra, lists = character(), auth = character())`.
   - Names compare case-insensitively.
   - The adapter's headers win: a record header with the name of one the adapter set is dropped.
     A record therefore never changes `content-type`, `accept` or `anthropic-version`, and never
     replaces the credential.
   - `lists` headers (here `anthropic-beta`) get the tokens of both sides, the adapter's first,
     each once.
   - While the adapter sends a credential, a record header named in `auth` (here `x-api-key`,
     `authorization`) is dropped, so two credentials are never sent ("never sends both"). Without
     a credential, it is sent as it is.
   - Of two record headers with the same name, the last is kept.

   `anthropic_build()` calls it with `lists = "anthropic-beta"` and
   `auth = c("x-api-key", "authorization")`. Tasks 5, 7 and 9 must use the helper instead of the
   plan's `c()`, with their own credential names (D-023 item 3).
2. **Nit: contradictory notes for an image-only tool result to a text-only model.** The tool
   result got "(see attached image)" followed by the omission note. Fix: the lead is added only
   when `images` is `TRUE`, that is, when an image block is attached.
