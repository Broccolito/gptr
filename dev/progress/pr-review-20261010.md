## Recommendation

The implementation is coherent, small enough for its behavior, and valuable for a novice opening
`peter()` without a configured model. I found no reproducible blocking implementation bug in this
review. Focused offline validation and changed-file lint pass. I would keep the feature, clarify
what CLI authentication does and does not establish, align the onboarding documentation with the
console contract, and retain a separate manual check before calling the guide fully validated.

## Resulting behavior

- `repl_main()` invokes setup before the banner and any chat input. The REPL reader closes even
  when setup returns early (`R/console-repl.R:599-615,724-727`).
- Setup runs only for an interactive, new console without an explicit or effective configured
  model. Existing sessions, `.stdin = TRUE`, explicit models and noninteractive workflows skip it
  (`R/console-repl.R:649-651`). Prompt-bearing calls do not enter this console route.
- The menu offers Codex CLI, Claude Code CLI, and manual API instructions. An available CLI that
  reports signed in, or reports unknown with a notice, saves its `.../default` model at user scope
  and continues to the console. Cancel, manual setup, missing CLI, non-CLI same-name override or
  explicit signed-out state returns to R without saving (`R/console-repl.R:652-719`).
- It accepts the shortcuts only for the expected `cli-codex` and `cli-claude` API names; there is
  no automatic selection or fallback to a same-name HTTP provider (`R/console-repl.R:655-663,693-697`).
- `gptr_providers(check_login = TRUE)` independently adds a `login` column. Both default flags
  remain FALSE, retaining the existing no-process/no-network listing contract
  (`R/provider-registry.R:1339-1364`).

## Safety and implementation boundaries

**Settings and context.** The only persisted setup change is a model patch through the existing
public `gptr_config(model = ..., .scope = "user")` path. Existing settings and egress keys remain
under the normal locked update (`R/console-repl.R:715-718`; unchanged `R/gptr-config.R:325-346`).
No egress acknowledgement is granted; `gateway_guards()` still invokes the separate acknowledgement
before automatic context (`R/gptr-gateway.R:642-649`). Changing the default applies across projects,
subject to the normal higher-precedence project/session/call settings.

**Login checks.** Help gates the status command. Codex uses `login --help` then `login status`;
Claude uses top-level `--help` then `auth status`. Each subprocess has a 3-second timeout.
Missing tools, unsupported help, parse errors, inconsistent status/JSON, non-0/1 exit codes,
timeouts and errors become `unknown`; only three state strings are returned
(`R/cli-common.R:254-279`). Availability is installation/cached status, not a full compatibility
check: no version/capability probe is automatically requested by setup.

**Subprocesses.** Existing `pcli_run()` carries executable/prefix arguments into `proc_run()` with
the appropriate scrubbed child profile; there is no shell or model prompt. Existing process code
provides null stdin, temporary stdout/stderr files deleted on exit, timeout handling and cleanup
of the process tree (`R/cli-common.R:232-235`; `R/proc-spawn.R:211-244`;
`R/auth-childenv.R:51-60,170-222`). Raw synthetic auth output did not reach console output in the
independent process tests.

**Model execution.** The CLI inference adapters, sandbox mapping, MCP capability routing,
permission gates, CLI budget controls and model resolution are unchanged. Native Ollama
preflight/locality protections remain in place. Setup does not install CLIs, log in, acquire
credentials, discover local models, or guarantee that a selected CLI will successfully chat.

## Material caveats and design alignment

1. **Authentication is broader than subscription sign-in.** The Codex parser deliberately accepts
   every `Logged in using ...` line, including an API-key report; its regression test explicitly
   requires this (`R/cli-common.R:274`; `tests/testthat/test-cli-login.R:31-34`). The picker therefore
   does not establish subscription billing. The original CLI notice says usage counts against a
   ChatGPT plan (`R/cli-common.R:427-429`), so documentation should explain this boundary or adopt
   a deliberate authentication-type policy. Actual paid inference with such a login was not run;
   this is an established classification issue, not a verified billing event.
2. **This changes the interactive entry experience from the original design.** The governing
   console descriptions describe a banner/REPL and deterministic default resolution, without a
   mandatory first-use picker (`dev/spec/03-architecture.md:1810-1831`,
   `dev/spec/04-interface-contract.md:999-1083,2777-2793`). The proposed behavior is reasonable,
   but the PR updates the provider-listing contract more completely than the console contract.
   Record setup invocation, skip conditions, early return and persistent user-scope effect in the
   normative console contract. Earlier implementation plans may remain historical.
3. **The listing exception is correctly made explicit.** Section 15 IC-65 now says the no-process
   guarantee requires both `check = FALSE` and `check_login = FALSE`; the optional listing column
   and helper are documented. No new package dependency, compiled code or hidden inference is
   introduced (`dev/spec/04-interface-contract.md:961-964,1255-1277,2899-2904,4680-4689`).
4. **The shared selector change is broader than onboarding.** Title line feeds are now rendered
   through `console_escape()`, while details/choices still go through `ui_escape()`
   (`R/console-ui.R:189-194`). Model-authored single/multiple-choice `ask` questions also use this
   selector (`R/console-ui.R:247-260`). Other control/bidi/zero-width escaping is retained and
   permission approval rendering remains separate; tests cover ESC escaping and injected label
   newlines. Consider documenting intentional multiline titles so this is not mistaken for a
   setup-only rendering change.
5. **First-class local providers remain usable but less visible in this guide.** The menu requires
   an explicit cloud CLI choice or manual API instructions, and offers no Ollama-specific path.
   This does not violate local-only preflight or silently choose cloud, but an Ollama example
   would better represent IC-74. It is a guide improvement rather than a required core change.

## Reset helper verification

`dev/reset-user-settings.R` defaults to a preview. `--apply` moves only user `settings.json` to a
unique same-directory timestamp/PID backup. `--restore` requires a backup in that same config
directory, first backs up current settings, and attempts rollback if replacement fails.
It does not touch CLI authentication storage (`dev/reset-user-settings.R:6-17,20-64`).

Independent temporary-fixture tests verified preview is read-only; apply/restore preserve exact
bytes including CRLF; replaced settings remain recoverable; name collisions keep distinct
backups; a restore source outside the config directory is rejected; nearby files remain intact.
These tests did not read/reset actual user settings. Rename-failure rollback and concurrent
writers were not fault-injected. Because this is a development helper that bypasses package
settings locks/cache, the guide should tell users to close active gptr sessions before reset and
start a fresh session afterward.
